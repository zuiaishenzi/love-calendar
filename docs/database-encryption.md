# V1.5.0 数据库加密与升级

数据库使用 SQLite3 Multiple Ciphers 的 ChaCha20-Poly1305 页面加密。账号邮箱、回忆、图片、提醒等数据库内容以及 WAL 都加密保存。登录密码继续使用 scrypt 哈希。

## 现有 Linux 部署

上传代码后执行原来的更新命令：

```bash
bash /opt/love-calendar/bin/update.sh --retry
```

更新程序先停止旧服务并备份，随后新服务启动时自动识别明文数据库。转换流程会检查并合并 WAL，制作副本、加密、完整性检查、生成加密备份，最后替换原数据库；转换前的原文件在验证成功前不会被覆盖。请勿同时运行两个服务迁移同一数据库。大图片较多时请预留至少两份数据库大小的额外空间，首次启动会比平时慢。

默认自动生成 32 字节随机密钥，存于：

```text
/opt/love-calendar/shared/data/.database-key
```

密钥权限为 600，随持久化数据目录保留。重建容器不更换密钥。密钥丢失或错误时服务会停止，不会清空数据库。务必另存一份密钥到安全位置；恢复数据库时必须配合原密钥。不要把密钥提交到 GitHub，也不要发给别人。

现有部署的 tar 备份包含整个 data 目录，因此包含密钥：这类备份能恢复数据，但不能抵御整份备份被盗。请将备份存放在受限目录或加密的备份存储中。数据库文件加密不等于整台服务器加密，持有密钥或服务器管理员权限的人仍能解密。

可选地，在首次升级之前，在服务环境中设置 `DB_ENCRYPTION_KEY`（64 位十六进制随机字符串），使用外部管理的密钥代替文件。这样 data 目录备份不含密钥，需单独备份此配置。已有加密数据库后不要随意新增、更改或删除这个配置；本版本不提供密钥轮换功能。QQ SMTP 授权码所在 `.env` 不由数据库加密保护。

## 备份与回退

自动生成的 `calendar.sqlite.before-encryption-*.sqlite` 和后续数据库级备份都是加密文件。恢复这些文件时先停服务，并使用相同密钥。账本号转换工具也已适配加密库，须先完成 V1.5.0 服务部署再运行。

升级程序在转换前创建的 tar 备份，以及更早版本的历史备份，仍可能是明文；升级不会擅自修改或删除它们。确认升级和数据核对无误后，自行将这些历史备份迁移到加密存储。转换过程中临时副本受到文件权限保护；如果进程被强制中断，可能留下 `.encrypting-*` 文件，应在确认当前数据库可用后清理这些临时副本。

不要直接用旧版本程序打开加密库。需要回退时必须停服务并恢复与旧版本匹配的升级前备份，不能只切换容器镜像。原更新程序启动失败时会恢复它创建的升级前备份。

## 验证

`npm test` 包含明文迁移、图片字节一致性、WAL 无明文标记、备份解密、重启读取、错误密钥和缺失密钥拒绝启动等测试。普通 SQLite 工具不能直接打开加密文件，需要支持相同加密格式及密钥的工具。
